# LifeWeeks

Telegram Mini App + бот «вся жизнь в неделях».

* Пользователь указывает дату рождения — приложение рисует его жизнь сеткой недель.
* Каждый вечер бот спрашивает «Как прошёл ваш день?» с кнопками 🙂 / 😐 / 🙁.
* Каждый понедельник утром присылает «Пошла N-я неделя вашей жизни» и ссылку
  на отчёт за прошедшую неделю с графиками внутри Mini App.

```
lifeweeks/
  backend/           FastAPI + aiogram + APScheduler в одном процессе
    app/
      main.py        точка входа: API, бот и планировщик
      api.py         REST для Mini App
      auth.py        проверка подписи Telegram initData
      bot.py         команды, кнопки оценки, тексты рассылок
      scheduler.py   кто и когда получает сообщение
      lifeweeks.py   вся доменная арифметика недель и отчётов
      db.py          asyncpg, запросы
      schemas.py     контракт запросов/ответов
      config.py      настройки из .env
    migrations/      SQL, накатывается автоматически при старте
    tests/           61 тест
  frontend/
    index.html       Mini App целиком
    vendor/          Chart.js 4.4.6
  deploy/
    lifeweeks.service
    nginx/lifeweeks.pukikuki.ru.conf
    install.sh
```

## Быстрый старт на сервере

```bash
git clone <repo> /root/lifeweeks-src
cd /root/lifeweeks-src/lifeweeks/deploy
./install.sh
# впишите BOT_TOKEN и DATABASE_URL в /opt/lifeweeks/backend/.env
systemctl restart lifeweeks
journalctl -u lifeweeks -f
```

Обновление кода потом: `./install.sh --update`.

Скрипт кладёт бэкенд в `/opt/lifeweeks`, фронт в `/var/www/lifeweeks`,
создаёт роль и базу `lifeweeks`, ставит systemd unit и nginx-конфиг.
Схему БД накатывает сам сервис при старте.

## Что меняется на сервере

**Nginx.** Сейчас домен `lifeweeks.pukikuki.ru` описан в двух файлах —
`sites-available/lifeweeks` и `sites-available/lifeweeks.pukikuki.ru`. Какой
из них выигрывает, зависит от порядка обхода каталога, поэтому оба удаляются
из `sites-enabled` и остаётся один конфиг. Мёртвый `location /n8n/` убран:
n8n не запущен, а порт 5678 теперь занимает бэкенд LifeWeeks.

**Порт 5678** переиспользован под python-бэкенд — он свободен, и старый
`proxy_pass` на него всё равно отдавал 502.

**Прочие проекты на сервере** (`tradingbot.service`, кроны `jilfond`, база
`marta_bot`) не затрагиваются: отдельная база, отдельный unit, отдельный
каталог.

## API

Все ручки требуют заголовок `X-Telegram-Init-Data` — это `Telegram.WebApp.initData`.
Сервер проверяет его HMAC-подпись ключом от токена бота и берёт `telegram_id`
оттуда. Идентификатор из тела запроса не используется нигде: иначе любой мог бы
прислать чужой id и прочитать чужую историю.

| Метод | Ручка | Назначение |
| --- | --- | --- |
| POST/GET | `/get-user` | профиль; создаёт запись при первом заходе |
| POST | `/set-birthdate` | `{birth_date}` — установить/изменить дату рождения |
| POST | `/rate-day` | `{date?, rating}` — чек-ин за день |
| POST | `/rate-week` | `{week_start, rating}` — недельная оценка (совместимость) |
| POST/GET | `/week-report` | отчёт за календарную неделю; без параметра — за прошлую |
| POST/GET | `/checkins` | `?from=&to=` — плоский список оценок |
| POST/GET | `/life-weeks` | агрегаты по неделям жизни для раскраски сетки |
| POST | `/settings` | таймзона, время рассылок, вкл/выкл уведомлений |
| GET | `/health` | проверка живости |

`rating` принимается как `good`/`neutral`/`bad`, как эмодзи `🙂`/`😐`/`🙁`
и как русские подписи — старый фронт слал разное.

Три ручки из исходного контракта (`get-user`, `set-birthdate`, `rate-week`)
сохранены как были, поэтому старый `index.html` продолжит работать, если
подменить только `CONFIG.API_BASE`.

## Решения по открытым вопросам ТЗ

**Часовой пояс — пользователя, а не сервера.** У каждого в `users.timezone`
своя зона (по умолчанию `Europe/Moscow`) и своё время рассылок. Планировщик
не имеет задачи «на 20:00»: раз в 5 минут он обходит пользователей и смотрит,
наступило ли нужное время *у них*. Иначе пользователь во Владивостоке получал
бы вечерний вопрос в час ночи.

**Регистрация — и в Mini App, и в боте.** Основной сценарий — онбординг в
приложении (`get-user` возвращает `birth_date: null` → показывается экран
ввода). Но бот принимает дату и текстом (`31.12.1990`, `1990-12-31` и
несколько других форматов): человек, который нажал /start и не открыл
веб-вью, не должен упереться в тупик.

**История смены даты рождения не ведётся.** Чек-ины хранятся по абсолютным
календарным датам, поэтому номер недели и вся сетка пересчитываются из новой
даты рождения детерминированно. Отдельная таблица истории дала бы данные,
которые негде показать.

**Пропущенный день — отдельная категория `skipped`.** День в прошлом без
оценки попадает в отчёт как «без оценки», а не исчезает: иначе неделя с одной
отметкой «хорошо» выглядела бы идеальной. Будущие дни недели помечаются
`future` и в статистику не идут вовсе.

## Две разные «недели»

Это единственное место, где легко запутаться.

* **Неделя жизни** привязана к дате рождения: неделя `i` — это дни
  `[birth + 7i, birth + 7i + 6]`. По ней строится сетка и фраза
  «пошла N-я неделя».
* **Календарная неделя** — понедельник–воскресенье. По ней строится отчёт,
  потому что рассылка приходит утром в понедельник.

Границы не совпадают, и это осознанно: сетка — про биографию, отчёт — про
прошедшие семь дней.

## Рассылки

Планировщик тикает раз в `SCHEDULER_TICK_MINUTES` (по умолчанию 5) минут.
Для каждого пользователя считает его локальное время и решает, пора ли.

Отправка защищена от дублей таблицей `notifications_log`: право отправить
резервируется вставкой `(user_id, kind, target_date)` *до* обращения к
Telegram, поэтому перезапуск сервиса или наложение тиков не приводят ко
второму сообщению. Если отправка сорвалась по временной причине
(флуд-контроль), резерв откатывается и попытка повторится в следующий тик.

Есть окно наверстывания — 3 часа для вечернего вопроса, 6 для недельного
отчёта. Если сервис лежал ровно в свой тик, сообщение всё равно уйдёт, но
вечерний вопрос никогда не придёт в три часа ночи.

Пользователь, заблокировавший бота, автоматически получает
`notifications = false` — иначе каждый тик тратился бы на заведомо
провальную отправку.

## Локальная разработка

```bash
cd backend
python3 -m venv venv && venv/bin/pip install -r requirements.txt
cp .env.example .env      # впишите BOT_TOKEN и DATABASE_URL
venv/bin/python -m app.main
```

Фронт ходит в API по относительному пути `/api`, поэтому для локальной работы
нужен один хост, отдающий и статику, и API — либо nginx, либо любой прокси.

### Тесты

```bash
cd backend
python -m unittest discover -s . -p 'test_*.py'
```

Доменные тесты и тесты подписи initData идут без базы. Сквозные тесты API
включаются переменной с DSN:

```bash
createdb lifeweeks_test
LIFEWEEKS_TEST_DSN=postgresql://lifeweeks@127.0.0.1:5432/lifeweeks_test \
    python -m unittest discover -s . -p 'test_*.py'
```

Сквозной набор гоняет полный путь: регистрация → дата рождения → чек-ины →
отчёт → настройки, плюс отказы (подделанный initData, чужой токен, оценка
будущего дня, дата раньше рождения, изоляция пользователей).

## Заметки по фронту

`frontend/index.html` — цельный Mini App без сборки: четыре экрана
(сетка, сегодня, отчёт, настройки), тема берётся из переменных Telegram.

Chart.js лежит в `vendor/`, а не грузится с CDN: Mini App не должен зависеть
от стороннего хоста, и у части пользователей CDN-домены недоступны.

`CONFIG.API_BASE` — относительный `/api`. Абсолютный URL пришлось бы править
под каждый стенд, а Mini App и API отдаёт один и тот же домен.

Пара неочевидных мест, которые легко сломать обратно:

* Даты разбираются вручную, а не через `new Date('2026-08-01')` — последнее
  даёт UTC-полночь и в отрицательных таймзонах уезжает на день назад.
* Номер недели считается по календарным суткам, а не по разнице
  миллисекунд, — иначе переход на летнее время раз в полгода сдвигает
  результат на неделю.
* Графики пересчитывают размеры при показе экрана: Chart.js замеряет
  контейнер в момент создания, а на скрытом экране ширина равна нулю.
* Плохой день на графике — это высота 1, а не 0: столбик нулевой высоты
  визуально неотличим от дня без отметки.
